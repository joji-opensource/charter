# Dev Charter v0.1 — build plan

version: draft 4 (after review ×2 and probe rounds 1 and 2; v0.1 focused on Claude Code)
date: 2026-10-25

The plan for Dev Charter's first release. It follows Dev Charter's own loop: plan → review ×2 → probe → build. The body is
always the plan of record; the review log (§9) and the probe results (§10) record what changed it and why.

## 1. Goal

A product team installs Dev Charter in an existing or new repository and, the same day, has:

- a plain-English feature list in their repository, readable by anyone;
- a generated spreadsheet that shows every feature, the code that builds it, the tests that prove it, and a status
  worked out from those tests and from people's sign-offs;
- Claude Code following Dev Charter's way of working, with no setup beyond installing Dev Charter and its plugin.

v0.1 is built and tested for Claude Code only (Joji, 2026-10-25). Nothing in it is specific to Claude Code where it
does not need to be: the rules live in `AGENTS.md` and the checks run in git, so other coding tools can follow in a
later release.

## 2. Requirements

- **R-01 Install like a customer.** `uv tool install dev-charter` (or `uv tool install git+https://github.com/joji-opensource/charter`
  before PyPI) gives a `dev-charter` command, with the stage guides inside it. *Done when:* a clean machine installs it
  and `dev-charter guide plan` prints the packaged guide. (Proven for the git form: P6.)
- **R-02 Set up any repository.** `dev-charter init` works in a single repository and in a root that holds several
  repositories, nested or side by side. *Done when:* it writes `charter.toml`, the `charter/` folder, the agent
  instructions (R-06), the git hooks (§5.7) and the `.gitignore` entries; running it twice changes nothing.
- **R-03 Features, promises, decisions, ideas as files.** One Markdown file per feature, promise and decision; one
  ideas file. `dev-charter feature new` hands out the next ID and writes the full template. *Done when:* a file written
  by a person or an agent from the template is read back without loss, and a malformed file produces a
  plain-English error naming the file and line.
- **R-04 The spreadsheet.** `dev-charter report` writes `LEDGER.xlsx` (Summary, Features, Promises, Code map,
  Decisions, Ideas) and `status.html`. Dev Charter sets every row height itself (P2). *Done when:* a person opens the
  demo store's file in Excel, Numbers and Google Sheets and finds it readable: wrapped text, coloured statuses,
  frozen header row.
- **R-05 Trace and calculated status.** Tags and test names as in §5.3, test results from JUnit XML, status by the
  rules in §5.4. *Done when:* on the demo store, turning one test from passing to failing turns its feature from
  Proven to At risk in the next report (shown in miniature by P3b).
- **R-06 Instructions in the repository.** After `dev-charter init`, Claude Code opened in the repository knows
  Dev Charter's rules and loads the full guide for each stage with `dev-charter guide <stage>`, even for a teammate who has
  not installed the plugin. Delivered through `AGENTS.md`, which Claude Code loads by itself. *Done when:* Claude
  Code, started fresh in the demo store and asked to plan a change without being told about Dev Charter, runs
  `dev-charter guide plan` and follows it. (Proven: P1, P1b.)
- **R-07 Checks.** `dev-charter check` validates files and the trace (§5.6). Runs in CI in every mode and before each
  commit in Standard and Strict.
- **R-08 Modes.** Light, Standard, Strict, set in `charter.toml`; Strict can be turned on for one session.
- **R-09 Claude Code plugin.** Part of the standard install. `/dev-charter:init` asks the setup questions in
  conversation and runs `dev-charter init`; `/dev-charter:feature` turns a plain-English request into a feature through
  `dev-charter feature new`; one skill per stage (`/dev-charter:plan`, `/dev-charter:review`, …) loads that stage's guide;
  `/dev-charter:status` and `/dev-charter:park`; the session starts with `dev-charter status --brief`; the Strict-mode edit
  guard. Rules never live only in the plugin: they are in `AGENTS.md` (R-06), so the plugin adds shortcuts and
  Strict mode, not knowledge. Each skill declares `allowed-tools` for exactly the `dev-charter` commands it runs
  (`Bash(dev-charter guide:*)`, `Bash(dev-charter feature new:*)`, …), never wider, so a person is not asked for permission
  at every step (P9).

## 3. Non-goals for v0.1

- **N-01** Two-way sync from the spreadsheet back to the files (`dev-charter import` is later).
- **N-02** Mapping existing code to features automatically. v0.1 lists untagged code so a person or agent can tag
  it; the mapping skill is v0.2.
- **N-03** Hosting, accounts, a web app. Dev Charter is files plus a command.
- **N-04** Task scheduling (dates, assignees, sprints).
- **N-05** Coding tools other than Claude Code (Codex, GitHub Copilot, Cursor and others): not tested, documented or
  supported in v0.1. Nothing is done to exclude them either.

## 5. Contracts

### 5.1 `charter.toml`

```toml
[product]
name = "Demo Store"
mode = "standard"                       # light | standard | strict
dev-charter = ">=0.1,<0.2"              # Dev Charter versions this project works with; checked on every command

[[repos]]
path = "."                              # relative to this file; one entry per repository
results = ["reports/junit/*.xml"]       # where that repo's test runner writes JUnit XML
# code  = ["src/**"]                    # optional; defaults: common source extensions outside test folders
# tests = ["tests/**"]                  # optional; defaults: tests/, test_*.*, *_test.*, *.test.*, *.spec.*

[words]
roles = ["customer", "store admin", "support agent"]
areas = ["Orders and delivery", "Checkout", "Accounts"]
internal = []                           # jargon that must not appear in plain-English text
```

### 5.2 Files in `charter/`

```
charter/
  features/F-014-track-my-order.md
  promises/P-002-only-see-your-own-orders.md
  decisions/DEC-031-delivery-dates-from-carrier.md
  ideas.md
  cards/CARD-007-order-status-page.md
  handoff.md
```

A feature file. The labels are fixed; a label's text runs until the next label or a blank line.

```markdown
---
id: F-014
title: Track my order
area: Orders and delivery
priority: Must                # Must | Should | Could
release: Spring launch
state: agreed                 # idea | agreed | live | parked | retired — set by people only
decisions: [DEC-031]
---

**As a** customer of an online store
**I want to** see where my order is and when it will arrive
**With** the current step (packed, shipped, out for delivery), the expected delivery date, and a text message
when it is out for delivery
**Must also** load in under 2 seconds on a phone · show me only my own orders
**So that** I don't have to contact support to ask where my package is

## Done means

- **a.** Every order shows its current step and expected delivery date
- **b.** A text message is sent when the order goes out for delivery
- **c.** Opening someone else's order shows a sign-in page, never their order

## Sign-offs

- 2026-10-24 · b · Joji John · received the text on a real phone during a staging order
- 2026-10-24 · proven · Joji John · watched the whole flow work on staging with a real order
```

A sign-off line is `date · <criterion letter or "proven"> · <person> · <what they saw>`. A criterion sign-off covers
checks that are not automated (a text arriving on a phone, a page loading fast enough on a real device).

`ideas.md` is one bullet per idea: `- 2026-10-25 · <idea> · from <card, feature or person>`. A decision file has
frontmatter `id`, `date`, `decided_by`, then **Decision**, **Instead of**, **Because**. A card has frontmatter
`id`, `serves` (criterion IDs), `state`, then **Goal**, **Plan**, **Done when**, and in Strict mode **Allowed
paths**. `handoff.md` holds only the latest state: done with evidence, in progress, parked, exact next step.

### 5.3 Tags

- **IDs** are `F-` or `P-` followed by three or more digits (`F-014`, `P-002`), with a criterion letter after a dot
  (`F-014.b`). Decisions are `DEC-nnn`, cards `CARD-nnn`.
- **Code.** A comment containing `serves:` followed by IDs: `# serves: F-014, P-002`. Only a `serves:` line with
  at least one well-formed ID counts (P4 found `serves:` in ordinary prose). Shared code that every feature relies
  on says `serves: foundation`; it is shown as *Shared foundation*, not as unexplained.
- **Tests.** The criterion ID inside the test's name, in whatever form the language allows: `test_F014_b_text_sent`,
  `it("F-014.b sends a text")`, `func TestF014B(t *testing.T)`, `testF014bSendsText`. Matched with
  `(?<![A-Z0-9])([FP])-?(\d{3,})(?:[._-]?([a-zA-Z]))?(?![a-z0-9])`: the prefix letter is upper case and may follow a
  lower-case letter (`TestF014B`); a check letter may not run on into a lower-case word (`F014_order` is F-014). Any
  parameter part in brackets is removed first (P3). IDs are looked for only on `serves:` lines and in test names,
  never elsewhere in code (P4 found linter codes such as `F401` and colours such as `f800`). The draft-3 pattern
  rejected `TestF014B` (found by stage 2's tests); the loosened one still finds no false ID among the 1,581 real test
  names of the 12-repository product P4 scanned.
- **Results.** JUnit XML, the default format of each runner (pytest needs no option: P3). A test case's IDs come from
  its name; its outcome from its `failure`, `error` and `skipped` children.

### 5.4 Status rules

Each criterion is:

- **failing** if any test tagged with it failed or errored in the latest results;
- otherwise **passing** if at least one tagged test passed, or a person signed it off;
- otherwise **unchecked**. Skipped tests count for nothing.

Then, per feature, the first rule that matches wins:

1. `state` is idea, parked or retired → that state.
2. Any criterion is failing and the feature is `live` or has a `proven` sign-off → **At risk**.
3. `state: live` → **Live**.
4. Every criterion is passing and there is a `proven` sign-off → **Proven**.
5. Every criterion is passing → **Built**.
6. Any code or test is tagged with the feature → **Being built**.
7. Otherwise → **Agreed**.

"Every criterion is passing" requires at least one criterion: a feature with no checks is never Built or Proven
(found while building stage 1).

Every status shows its count beside it (*2 of 3 checks passing*), so a Live or Proven feature that gained a new,
unchecked criterion says so. Each repo's results show the time they were written; `dev-charter check` warns when a
repo's results are older than its latest commit.

### 5.4a Where a feature is built (stage 2)

The spreadsheet names code the way a product owner can follow it (Joji, 2026-10-25):

- **Built in** (Features tab): each repository's name and the files tagged with the feature,
  `shop-api: orders/status.py · notifications/sms.py`.
- **Code map** tab: one row per tagged or untagged code file: repository, file, the features it serves (or *Shared
  foundation*, or *Unexplained*), and a link that opens the file on GitHub at the exact commit the report was built
  from.
- A repository's name and web address come from its git remote (`origin`); `[[repos]] name` and `url` in
  `charter.toml` override them. A repository without a web address shows the path without a link.

### 5.5 Agent instructions

- `dev-charter init` writes a managed block, between `<!-- dev-charter:start v<version> -->` and `<!-- dev-charter:end -->`,
  into `AGENTS.md`, creating the file if needed and never touching text outside the block. At most 40 lines: what
  Dev Charter is here, the rules below, and the commands.
- The rules: every change serves a feature or promise; run `dev-charter status --brief` before starting work; load
  `dev-charter guide <stage>` before each stage; add features with `dev-charter feature new` (never invent an ID); tag new
  code and name tests with criterion IDs; park ideas with `dev-charter park`; run `dev-charter check` before saying work is
  done; never write a sign-off, never set `state`, never commit with `--no-verify`.
- `CLAUDE.md` is not touched: Claude Code loads `AGENTS.md` on its own (P1, P1b).
- `dev-charter sync` refreshes the block after an upgrade; `dev-charter check` warns when the block's version differs from
  the installed Dev Charter.
- The full guides live in the installed package (`dev-charter guide <stage>`), so every project gets the same guides
  and upgrading Dev Charter upgrades them everywhere.
- The `feature` guide requires the agent to list, in its reply, any criterion the person did not ask for, so the
  person keeps or removes it (P5).

### 5.6 What `dev-charter check` checks

| Finding | Light (CI) | Standard / Strict (before commit) |
|---|---|---|
| Malformed file, duplicate ID, unknown ID on a `serves:` line | error | error |
| A new code file with no `serves:` tag | warning | error |
| A changed code file with no `serves:` tag | warning | warning |
| An unknown ID in a test name | warning | warning |
| A word from `[words] internal` in plain-English text | warning | warning |
| A feature file over 250 words | warning | warning |
| Stale results, out-of-date instruction block, a repo without the commit check | warning | warning |

`dev-charter check --staged` looks only at what is about to be committed.

### 5.7 When things run

- **Before each commit** (Standard and Strict): a git `pre-commit` hook runs `dev-charter check --staged`.
- **After each commit** (every mode): a git `post-commit` hook runs `dev-charter report --quiet`, so the spreadsheet on
  each machine is never older than the last commit. The scan takes under a second on 170,000 lines (P4).
- **In CI:** `dev-charter check` and `dev-charter report`; the spreadsheet is attached to each release.
- **On demand:** `dev-charter report`, `dev-charter status`.
- **Claude Code plugin:** `SessionStart` prints `dev-charter status --brief` into the session; in Strict mode,
  `PreToolUse` on Edit and Write denies writes outside the active card's allowed paths and any edit that adds a
  sign-off line. Nothing runs on `Stop` or `SessionEnd` (Stop fires after every turn; SessionEnd has 1.5 seconds).

Hook installation, in each repository listed in `charter.toml`: the hooks folder is the one
`git rev-parse --git-path hooks` names, which honours `core.hooksPath` (P8). If a hook of the same name already
exists, or the repo uses the pre-commit framework, Dev Charter does not overwrite it: it prints the one line to add.
Each hook calls `dev-charter … --root <relative path to the charter root>` and, when `dev-charter` is not installed,
prints one line saying so and lets the commit through. A repository listed in `charter.toml` that is only a folder
inside a bigger git repository (like `examples/demo-store` inside Dev Charter's own) gets no hooks: they would check
every commit of the bigger repository against the folder's charter.

Code that existed before Dev Charter is already committed, so it never counts as new: adopting Dev Charter in an
existing product does not stop the next commit. `check` reports such files once, as a count, and the Code map lists
them as Unexplained.

### One version number

- `pyproject.toml`'s version, `plugin/.claude-plugin/plugin.json`'s version and the git tag `vX.Y.Z` are the same
  number; the release workflow stops if they differ. The command and the plugin are always released together.
- The plugin's session-start hook compares `dev-charter --version` with its own version and, when they differ, says in
  one plain line which one to update.
- A project's `charter.toml` names the Dev Charter versions it works with; every command checks it.
- Semantic versioning. While 0.x, a minor release may change behaviour, always with a note in `CHANGELOG.md`.

### Branches

`main` holds only released code; work happens on `dev`; a release merges `dev` into `main` and tags it. Reason:
people who add the plugin get it from the repository's default branch, so unreleased plugin changes on `main` would
reach them before the matching command is on PyPI. (Assumption: the marketplace follows the default branch. To be
probed in stage 3 by installing from GitHub.)

### Release pipeline (GitHub Actions)

- **`ci.yml`, on every push and pull request:** `uv sync --locked`; ruff; pytest on Python 3.11 to 3.13 on Linux and
  macOS; `uv build`; `twine check`; `claude plugin validate .` and `claude plugin validate ./plugin`; the three
  version numbers agree.
- **`release.yml`, on a `v*` tag:** build once and keep the files; wait in the `pypi` environment for Joji's
  approval; publish with PyPI trusted publishing (no stored token) and its signed attestations; create the GitHub
  Release with notes and files.
- Actions pinned to commit hashes; Dependabot keeps the actions and `uv.lock` current.

### What every package contains

`LICENSE` and `NOTICE` (declared with `license-files`; P10), the README as the PyPI page with absolute links, the
guides and templates as package data, and the copyright header in every source file.

### The name

The framework was first named Charter. PyPI refused `charter` in the pending-publisher form ("This project name isn't
allowed"): no existing project collides with it, so it is on PyPI's own list of disallowed names. The word is also
crowded in this exact space (`charter-intent`, "executable design intent for AI-coded repos"; `project-charter`, an
AI agent governance engine; `charter-governance`; and `charter-cli`, which already installs a `charter` command).
Renamed **Dev Charter** (Joji, 2026-10-25): `dev-charter` is free on PyPI and TestPyPI, with no look-alike name.

## 9. Review log

### Pass 1 (on draft 1)

Problems first; each fix is in the body above.

1. **Instructions only reached Claude Code** (draft 1 §5.5 wrote `CLAUDE.md`), contradicting R-06. → `AGENTS.md`
   managed block; `CLAUDE.md` untouched; guides served by `dev-charter guide`.
2. **"After every session" depended on Claude Code's `Stop` hook**, which fires after every turn, and other tools
   have no such hook. → git `post-commit` rebuilds the spreadsheet; `pre-commit` runs the check. Works with every
   tool and with people.
3. **Non-automatable criteria could never pass** (a text arriving on a phone, speed on a real device). → criterion
   sign-offs (§5.2) count as passing.
4. **Skipped tests, stale results and Live features with gaps were undefined.** → §5.4: skipped counts for nothing;
   results show their time and stale ones warn; every status shows its check count.
5. **Shared code had no honest tag**, so it would be flagged unexplained forever or tagged with a random feature. →
   `serves: foundation`.
6. **An existing codebase would fail every commit** if untagged changed files were errors. → only new untagged files
   stop a commit; changed ones warn.
7. **Duplicate IDs from parallel branches** were not caught. → `dev-charter check` error; `feature new` hands out IDs.
