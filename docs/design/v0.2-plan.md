# Dev Charter v0.2 — Claude Code and Codex, taking turns on one product

version: built as 0.2.0 (draft 5 approved by Joji; four stages built and shown, §7)
date: 2026-10-27

Joji asked (2026-10-27): "Can you create a plan for dev-charter to support both parallel and taking turns on the same
folder codebase for Claude code and codex." After two review passes showed that parallel work in one folder carries
most of the risk and complexity, Joji chose (same day) to keep Codex support and taking turns, and to park parallel
work (§4, N-06). This plan follows Dev Charter's own loop: plan → review ×2 → probe → build. The body is the plan of
record; the review log (§10) and the probe results (§11) record what changed it and why.

## 1. Goal

A person works on one product with Claude Code and Codex, taking turns: one agent does a stage of a task card, the
other does the next (Claude Code plans and builds, Codex reviews; or the other way round). Both agents follow the
same rules from the same `AGENTS.md`, with the same guardrails, and each says when its guardrails are not running.
The card shows which agent did which turn.

What a person working with one agent will notice: the agent records a turn when it hands a card on; `status --brief`
warns when the guardrails are not running; in Strict mode, the agent can no longer edit `charter.toml` or
`.dev-charter/`, nor turn Strict mode off; and child repositories get a short `AGENTS.md` pointer.

## 2. What is true today (0.1.3)

From the code, and from the probes of 2026-10-27 (§11):

1. **The rules reach Codex** through `AGENTS.md`, which it reads on its own; the git hooks and CI do not care which
   agent made a change; `dev-charter` runs inside Codex's default sandbox from the product's root (C6).
2. **The guardrails do not reach Codex.** Codex 0.164 runs plugin hooks with the same events and answers as Claude
   Code (C1–C3), but reports a file edit as `apply_patch`, with the patch text in `tool_input.command` and no
   `file_path`. `strict.decide` and `remind.note` read only `file_path` (the guard also `notebook_path`), so under
   Codex, Strict mode allows every edit and the reminder to tag code stays silent, without a word (C0, C1).
3. **The plugin is Claude Code's only**, though Codex can install the same folder with one more manifest (C5). Codex
   runs a hook only after the person trusts it in `/hooks`, and again after any change to the hook; until then it
   skips it without a word (C5).
4. **Strict mode can be undone by the agent it constrains:** the guard lets any edit to `.dev-charter/` through,
   watches no shell command, and does not stop `dev-charter strict off`. Its state and sign-off checks also read the
   file differently from Dev Charter's own reader: a duplicated quoted `"state"` key or an indented sign-off line gets
   past the guard and still counts (review pass 3).
5. **Codex started inside a child repository sees none of the product's rules** (C7). Claude Code started there
   reads the root's `AGENTS.md` (C7).
6. **Codex's sandbox refuses some writes `dev-charter` needs, and the user gets a Python traceback:** writes outside
   the folder Codex started in (C6), and any write inside `.git`, so `init`, `sync` and an upgrade cannot install the
   git hooks under Codex even from the root (C12).
7. **Nothing records which agent did which stage.** Git records the person who commits.
8. **Upgrading is blocked by the project's own pin.** `charter.toml` pins `dev-charter = ">=0.1,<0.2"`; with 0.2
   installed, every command that opens the project, and the commit check, refuses until someone edits the range
   (`guide`, `guard`, `remind` and `init` do not check it).
9. **An agent's shell can carry both agents' variables** when one was started from the other's shell (C6), and
   Codex's sandbox forbids `ps` (C4), so neither variables nor parent processes reliably say which agent is calling.
   A hook's payload does: Codex's carries `turn_id` and `model`, Claude Code's `prompt_id` and `effort` (C1, C4).
10. **A plugin's hooks and the agent's shell can run different `dev-charter`s.** Codex's shell is a login shell that
    rebuilds `PATH`; in C1 its hooks ran one `dev-charter` and its commands another.

## 3. Requirements

R-01 to R-25 are v0.1's (`v0.1-plan.md`).

### Part A — Codex has what Claude Code has

- **R-26 One reader for every edit.** A new `edits.py` turns a hook's payload into a list of changes, one per file:
  the operation (add, update, delete, move), the path and the new path of a move. Claude Code's `Write`, `Edit`,
  `MultiEdit` and `NotebookEdit` give one change each (a notebook by path only). Codex's `apply_patch` is read with a
  stated grammar (`*** Begin Patch`, `Add File`, `Update File` with `Move to`, `Delete File`, `@@` hunks, `*** End of
  File`, `*** End Patch`), paths relative to the payload's `cwd` (shapes captured in C1). One refused file refuses the
  whole tool call (C1). For a feature or promise file, the guard needs the text after the edit: for Claude Code it is
  rebuilt as today (`strict._proposed` moves here); for Codex, each hunk is applied to the file on disk only where its
  context matches exactly once, and anything else is refused in Strict mode. The Strict-mode rules then compare the
  file before and after **with Dev Charter's own reader** (`store.parse`): a change of `state`, a new sign-off, a
  deleted or moved feature or promise file are refused. `store.parse` rejects duplicate keys, so a file the guard
  and the reader would read differently is malformed. *Done when:* every Strict-mode test passes with both payload
  shapes, including a half-line edit of `state:`, a deleted `state:` line, a duplicated quoted key, an indented
  sign-off and a deleted feature file, and a Codex patch with one allowed and one refused file changes nothing.
- **R-27 One plugin, both agents, old command names.** `plugin/` gains `.codex-plugin/plugin.json` beside
  `.claude-plugin/plugin.json`; both use the one `skills/` folder and the one `hooks/hooks.json`. The repository root
  gains `.agents/plugins/marketplace.json` beside `.claude-plugin/marketplace.json`, both pointing at `./plugin`
  (§5.2). The hooks keep calling `dev-charter guard` and `dev-charter remind`, so a new plugin with an older
  `dev-charter` still guards Claude Code's edits as today; the guard now also watches shell commands. *Done when:*
  `claude plugin validate` passes; Codex adds the marketplace, installs the plugin and lists its skills; once its
  hooks are trusted, the guard refuses a Strict-mode edit in Codex (all proven in C5 and C1).
- **R-28 Guardrails that say when they are off.** For each shell command it sees, the guard notes the agent (from the
  payload, §2.9), the session and the command, appended to a short log, `.dev-charter/recent-commands.jsonl` (trimmed
  to its newest 200 notes past 64 KiB). `status --brief`, run by an agent, looks for the note about itself: the same
  command, seconds ago, from its own session, which its shell names (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`, the
  ids the hooks receive, C13), so two agents in one folder never answer for each other. If there is none, the guard
  did not run for this command, and it says so (§5.4). The status printed at session start skips this line (no command has been
  guarded yet) and instead says when the plugin and `dev-charter` versions differ, and the session-start hook itself
  says when `dev-charter` is not installed. *Done when:* in Codex, before its hooks are trusted, `status --brief` says
  the guardrails are not running; once trusted, it does not; after a resume, it still does not (C4, C5).
- **R-29 Strict mode cannot be undone by the agent.** In Strict mode, the guard refuses an agent's edits to
  `charter.toml` and `.dev-charter/`, shell commands other than `dev-charter` that name either, and `dev-charter
  strict off`. Only a person turns it off, from their own terminal. This is a guardrail for an agent that follows
  its rules, not a wall: a shell command can still change a file (N-09).
- **R-30 Words that fit both.** Guides, command help, plugin descriptions and the README say "the coding agent" where
  any agent is meant, and name an agent only where what to do differs (installing the plugin, calling a skill,
  trusting hooks). The README gains a Codex section. A test fails when a guide names one agent outside a section about
  that agent.
- **R-31 Child folders point to the root.** `init` and `sync` write a short block into `AGENTS.md` in each listed
  folder where Codex would not find the root's: one that is the top of its own git repository, or that is not inside
  any git repository. The block uses the same markers as the root's (§5.3). `check` reports a missing or outdated
  block, an `AGENTS.override.md` (Codex reads it instead), and a managed block that starts beyond Codex's 32 KiB
  instruction limit. *Done when:* Codex started in a child repository follows the block to the root's rules and tells
  the person to start from the root (C7).
- **R-32 Plain words when a write is refused.** When the operating system refuses a write, `dev-charter` names the
  file and the system's reason, and gives the remedy that fits: run by an agent, a refused write in `.git` means
  running the command yourself in a terminal (Codex's sandbox keeps agents out of `.git`), and any other means
  starting the agent in the product's root folder or running the command yourself (an agent's sandbox lets it write
  only inside the folder it was started in, whichever folder it runs a command from); run by a person, checking
  that they may write there. Never a traceback. `init` and `sync` carry on past git hooks they cannot write, say so,
  and can be run again to finish.

### Part B — Taking turns

- **R-33 Turns on the card.** `dev-charter card turn CARD-nnn --did "<what this turn did>"` adds a line to the card's
  new `## Turns` section: `- 2026-10-27 10:40 · Codex · review pass 2`. The agent is taken from the guard's note about
  this command (R-28); with no note, from the one agent whose variable is set; otherwise, or when run by hand, the
  person's git name. The ship guide asks for it whenever an agent hands a card on or stops; a review done read-only
  is recorded by whoever writes it into the card, naming the reviewer in `--did`. *Done when:* a card handed from
  Claude Code to Codex shows both turns with the right agents, also when Codex was started from Claude Code's shell
  (C4).
- **R-34 A second review that does not start from the first.** The review guide says: when a pass on the card was
  written by another agent, write your pass from the plan and the code before you read theirs. The handoff is one at
  a time: the first agent records its turn and stops changing files; the person starts the other agent in its own
  terminal; the first resumes only after the second has recorded its turn. Dev Charter starts no agent itself.

### Part C — Upgrading

- **R-35 From 0.1 to 0.2 in one command.** When the installed Dev Charter is newer than the project's pin allows, the
  refusal names `dev-charter sync --upgrade`, which then runs anyway. It refuses to move a pin backwards (a project
  that needs a newer Dev Charter is told to install it). It works out every change first, then writes them, the pin
  last: the git hooks (never one that is not Dev Charter's), the `AGENTS.md` blocks (never one a newer Dev Charter
  wrote), the install range in a workflow `dev-charter ci` wrote (only that line, only if it is still Dev Charter's),
  and the pin line of `charter.toml` (only that line). Run again after a failure, it finishes the job. It lists what it
  changed and what the person must still do: update the plugin in each agent, trust the changed hooks in Codex, and,
  under Codex, run it from their own terminal (R-32). *Done when:* a 0.1.3 project with hooks and a CI workflow
  upgrades in one command and its next commit is checked; a failure after each write is finished by a second run; a
  project pinned to a newer version is refused.

## 4. Non-goals

- **N-06 Parallel work in one folder (parked by Joji, 2026-10-27).** Two agents at once need ownership of cards,
  fences around each other's files, a lock on every shared write, protection for unfinished work that outlives a
  session, and a guard on shell commands, and they would still disturb each other's test runs and formatters. Review
  pass 2 found the design's problems were structural (§10). If it comes back, the likelier path is one worktree per
  agent, which for a product of several repositories first needs a worktree in each of them (C10 shows where Codex
  puts its worktrees).
- **N-07 Running agents.** Dev Charter does not start, schedule or message agents.
- **N-08 Other agents** (GitHub Copilot, Cursor, Gemini): not tested. Nothing excludes them: the rules are in
  `AGENTS.md`; R-28 and R-33 name only the agents they know, and "an agent" otherwise.
- **N-09 Guarding every shell edit.** `sed -i`, a formatter or a script can change any file; no hook can read every
  command. So it is today in Claude Code.
- **N-10 A broken Python.** If `dev-charter` cannot start at all, a hook cannot refuse anything; R-28 makes that
  visible instead.

## 5. Contracts

### 5.1 The card

`templates/card.md` gains, after `## Handoff`:

```
## Turns

<!-- Written by `dev-charter card turn`: date time · agent · what the turn did -->
```

A card without the section gets it on its first turn. `--did` is reduced to one line.

### 5.2 The plugin

`plugin/hooks/hooks.json`, for both agents:

| Event | Matcher | Runs |
|---|---|---|
| SessionStart | all | `dev-charter status --brief --session-start`; when that `dev-charter` is too old to know `--session-start` (it exits 2), a line saying to upgrade it, then `dev-charter status --brief`; when `dev-charter` is not found, a line saying the plugin needs it (`uv tool install dev-charter`) |
| PreToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|apply_patch\|Bash` | `dev-charter guard` |
| PostToolUse | `Edit\|Write\|MultiEdit\|apply_patch` | `dev-charter remind` |

Each keeps today's form, ending `; exit 0`. Old and new plugins and commands work in any combination, with the newer
side saying what to update: a newer plugin finds an older command by its refusal of `--session-start`; a newer
command reads the plugin's version from the plugin's own manifest, since both agents give a hook the plugin's folder
(`CLAUDE_PLUGIN_ROOT`; Codex also `PLUGIN_ROOT`, as seen in C1); and an older plugin, which does not watch shell
commands, leaves no note, so the newer command's `status --brief` says the guardrails are not running.

What the guard does when something fails:

| Case | Answer |
|---|---|
| Not inside a product (no `charter.toml` above) | allow |
| `charter.toml` cannot be read | refuse every edit except to `charter.toml`, saying why |
| `.dev-charter/strict` cannot be read | treat Strict mode as on |
| Strict mode on, and the payload, a patch or the guard itself fails | refuse, saying why |
| Strict mode off, and the same | allow, as today |

With Strict mode off, the guard on a shell command only writes its note, so it costs little on each command (C9:
124 ms, against 104 ms for today's guard on an edit; nearly all of both is starting Python).

`plugin/.codex-plugin/plugin.json`: `name`, `version`, `description`, `author`, `homepage`, `repository`,
`license`, `"skills": "./skills/"`, `"hooks": "./hooks/hooks.json"`, and `interface` (`displayName`,
`shortDescription`, `category`). `.agents/plugins/marketplace.json`: `name: "dev-charter"`, `interface.displayName`,
and one plugin with `source: {"source": "local", "path": "./plugin"}`, `policy: {"installation": "AVAILABLE",
"authentication": "ON_INSTALL"}` and `category: "Developer Tools"` (C5 installed exactly these). The release workflow
checks both manifests' versions against the package's.

Skills: the `ship` skill may also run `dev-charter card turn`. A skill never puts `$ARGUMENTS` inside a command; it
says where the person's words come from and shows the command with a placeholder: "Take the idea from what the person
asked (in Claude Code it is here: $ARGUMENTS) and run `dev-charter park "<the idea>"`." C5 showed Codex already fills
such a placeholder correctly, quotes included; this wording makes it the stated rule. The commands guide gives each
agent's way to call a skill (`/dev-charter:plan` in Claude Code; in Codex, `dev-charter:plan`, C5).

### 5.3 `AGENTS.md`

The root's managed block gains one rule (it stays under 40 lines):

- When you hand a task card on or stop working on it, record your turn:
  `dev-charter card turn CARD-nnn --did "<what you did>"`.

The child block (R-31), from `templates/agents_child_block.md`, with the same markers as the root's (proven in C7):

```
<!-- dev-charter:start v0.2.0 -->
## Dev Charter

This repository is part of <product>. Its rules are in `<path>/AGENTS.md`: read that file now and follow it.
Work on <product> is started from `<path>`; if you were started inside this repository, tell the person before
changing anything.
<!-- dev-charter:end -->
```

`agents.block_state` and `write_block` take the expected text, so the same code writes, checks and refreshes both.

**C1 — Codex's hook payloads.** *Method:* the prototype logged every hook payload while Codex added, updated, moved
